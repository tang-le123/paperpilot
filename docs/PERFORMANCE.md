# PaperPilot 性能评估

## 结论

**当前版本偏慢，不适合宣称“实时交互”。**

30 条 arXiv 评测（阈值 0.35）实测：

```text
平均延迟：17.96 s
p50：18.98 s
p95：26.21 s
最慢：36.05 s
```

> 这是“补证上限优化”前的 30 条数据。  
> 优化后抽样两条单跳问题约 10.9–11.6 s，但还没有重新跑完整 30 条。

这是端到端 `/chat` 延迟，包含：

```text
检索 → 精排 → 生成 → 引用校验 → partial 二次检索 → 补证改写 → 再次校验
```

---

## 延迟构成（估算）

当前没有在每个阶段打点，以下是基于代码路径的估算，不是精确 profile：

| 阶段 | 估算 | 说明 |
|---|---:|---|
| Query embedding + 向量检索 | 1–3 s | bge-m3 + Chroma |
| BM25 / RRF / rerank | 1–4 s | reranker 在 CPU |
| DeepSeek 生成 | 4–8 s | 网络模型调用 |
| 引用校验 | 2–5 s | 批量 LLM 审核 |
| partial 二次检索 | 1–3 s | 每个 partial claim 一次 |
| 补证改写 | 5–12 s | 第二次 LLM 调用 |
| claim 拆分 | <0.1 s | 本地规则 |

所以慢的核心不是数据库，而是：

```text
一条回答可能触发 3–4 次 LLM 调用
+ 一次 CPU rerank
+ 多次 per-claim 检索
```

---

## 性能优化（已做）

1. 只有答案**会被门控**时才做 partial 二次检索和补证；
2. 最多补 2 个 partial claim，最多 4 个额外 chunk；
3. 支持率已高于阈值时，不再做 repair；
4. 回答仍是 SSE 流式，生成阶段可以先看到 token。

---

## 下一步优化

### P0：异步校验，先展示后校验

当前为了 gate，必须等 verifier 结束才发 final。  
可以改成：

```text
token 流式展示
→ final 先展示“待校验”
→ verifier 异步完成
→ 推送 verification 事件更新徽章
→ 若低于阈值，再折叠/警告
```

目标：

```text
首 token < 2 s
p50 端到端 < 10 s
```

### P1：减少 LLM 调用次数

```text
verifier 与 claim 检查合并成一次结构化输出
repair 只在 support_rate 低于阈值时触发（已做）
高频问题缓存
```

### P1：reranker 提速

```text
ONNX / GPU
更小 reranker
减少候选数
```

### P2：检索并行

```text
多篇论文 per-paper 检索并行
BM25 与向量并行
```

### P2：静态缓存

```text
热门论文的 chunk/BM25 缓存
相同 query 的检索缓存
```

---

## 质量与性能是两件事

```text
性能：p50 19 s，偏慢
质量：15/30 通过，citation support 0.37
```

两者都不能说“很好”。

但这不是同一个问题：

- 性能慢：主要是校验链路和多次 LLM 调用；
- 质量低：主要是检索证据、verifier 严格度和 claim 对齐。

---

## 面试表述

> 这个原型在有引用校验的情况下 p50 约 19 秒，确实不适合实时产品。  
> 我把它拆成检索、生成、校验、补证四段，先做了“只在会被门控时补证”的优化，下一步会把校验异步化、首 token 先出。  
> 我不会把 19 秒说成“性能优秀”，但我知道它慢在哪、怎么降。
